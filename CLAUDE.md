## What This App Is

ApexSight is a **native iOS security camera viewer** for [Frigate NVR](https://frigate.video).
Frigate runs locally on the user's home network. The app connects directly — no cloud, no
accounts, no telemetry. It is a premium, dark-glass, content-forward camera app. The cameras
are the hero. Everything else is chrome.

**Bundle ID**: `com.brandontoth.apexsight.native`
**Scheme**: `ApexSightNative`
**Deployment target**: iOS 17.0 (broad support) — but adopt **Liquid Glass and other iOS 26+
APIs behind `if #available(iOS 26.0, *)`** so the app is cutting-edge on the user's device
(iOS 26/27) while still installing on older ones. The simulator is iOS 26.5, so Liquid Glass
IS screenshot-verifiable — always verify it visually.
**Swift**: 5.10
**Version/build**: set in `project.yml` (`MARKETING_VERSION` / `CURRENT_PROJECT_VERSION`); the
Info.plist keys derive from them — never hardcode `CFBundleVersion` (that bug shipped build 1).
**Project file**: `native-ios/ApexSightNative.xcodeproj` (generated by xcodegen from `native-ios/project.yml` — run `xcodegen generate` after ANY new file or project.yml change)
**Repo root**: wherever you cloned it (`~/apexsight` on the user's Mac)

## Stream Architecture

Cameras load via **HLS → MJPEG cascade**, with an optional **sub-second WebRTC overlay** on top.

- **Primary**: `HLSLivePlayerView` (AVPlayer, exponential-backoff reconnect, main↔sub stream toggle)
- **Sub-second overlay**: `RealtimeVideoController` (recvonly go2rtc WebRTC; fullscreen + muted only;
  renders OVER the HLS layer when it gets a frame, HLS keeps running underneath as the fallback). NOT
  removed — it's the low-latency path. Cannot be render-tested on the simulator (the sim can't HW-decode
  WebRTC video for ANY camera — even a known-good one logs `no frame ❌`); confirm on a real device.
- **Fallback**: `MJPEGStreamView` (frame-by-frame MJPEG, off-main decode — Frigate's LOW-RES detect
  stream, so this is a quality downgrade; it should be a genuine last resort, never a hair-trigger)
- **Static**: `CameraSnapshotView` / `RemoteImage` (latest.jpg from Frigate)
- **Full-screen viewer**: `LiveStreamView` (wraps HLSLivePlayerView with chrome overlay, PTZ, timeline)

**go2rtc source gotcha (cost several builds — do not rediscover):** iOS AVPlayer can only decode go2rtc
HLS whose stream is routed through ffmpeg (`ffmpeg:<src>#video=copy#audio=aac`). A **raw RTSP passthrough**
go2rtc stream (`- rtsp://…`) makes AVPlayer report `.playing` but **never paint a frame** (presentationSize
stuck ~128×96, `isReadyForDisplay`/`videoReady` never true — you see the snapshot placeholder, not live),
so the app silently drops to low-res MJPEG. A camera with a long keyframe interval (the Scrypted-bridged
doorbell, ~4s GOP) needs an actual short-GOP re-encode, not just a copy-repackage. The verification signal
is `videoReady==true` + a real `presentationSize` — a sharp screenshot is the snapshot and proves nothing.
See `[[apexsight-ios]]` memory for the exact per-camera go2rtc config.

The cached snapshot should be visible **immediately** behind the HLS player so the camera
tile never looks empty. The live stream fades in over it when AVPlayer reports `.playing`.

**Stream quality rule (don't regress):** the camera **wall/grid plays the lighter `_sub`
stream** (`preferSub: true`) so many feeds stay smooth — an iPhone can't sustain ~8
simultaneous full-res HEVC decodes. The **full-screen viewer plays the full-res `main`
stream** for quality. `recordingHLSURL(camera,start,end)` is VOD for any time window; this
powers `RecordingBrowserView` (the recording timeline scrubber).

## Design System — GlassTheme

**Philosophy**: Dark-first. Cameras are the hero. Chrome is minimal.
No heavy gradients on UI chrome. No colored shadows. No white cards.

**Liquid Glass (iOS 26+)**: chrome surfaces use real Apple **Liquid Glass** via the shared
`.liquidGlass(in:tint:interactive:fallbackMaterial:)` modifier (in GlassTheme.swift), which calls
`glassEffect(_:in:)` on iOS 26+ and falls back to the dark frosted material + top-lit edge below
that. `GlassCard`, `GlassButtonStyle`, and control pills/overlays route through it, so adopting
glass app-wide is one call site. For multiple adjacent glass elements that should morph/blend,
wrap them in a `GlassEffectContainer`. Prefer compact **inline** nav titles (the user dislikes the
big large-title bar). Always screenshot-verify glass on the iOS 26.5 sim — regular glass over the
near-black background should read as a subtle lit pane, never a white card; tune tint/`.clear` if needed.

```swift
// Backgrounds (dark, layered)
GlassTheme.background     // app bg: near-black blue-tinted
GlassTheme.surface        // card bg
GlassTheme.surfaceHigh    // raised elements, skeletons

// Text
GlassTheme.primary        // near-white
GlassTheme.secondary      // 62% white
GlassTheme.tertiary       // 34% white

// Accents (use sparingly — one accent is premium)
GlassTheme.accent         // brand cyan-blue
GlassTheme.green          // live / connected
GlassTheme.orange         // motion / alert
GlassTheme.red            // recording / error
GlassTheme.separator      // 8% white — hairline only

// Spacing (4pt rhythm)
GlassTheme.Space.xs/s/m/l/xl/xxl  // 4/8/12/16/20/24

// Corner radius
GlassTheme.Radius.card    // 20 — large cards
GlassTheme.Radius.tile    // 18 — camera tiles
GlassTheme.Radius.chip    // 11 — small pills
```

**Components**:
- `GlassCard` — surface card with hairline border, no shadow
- `GlassBackground` — full-screen bg with radial gradients
- `PillButtonStyle` — capsule button with tint
- `SectionHeader` — bold section label
- `SkeletonView` — loading placeholder with shimmer

**Tab bar**: `.ultraThinMaterial`, dark color scheme. Never override with a solid color.
**Nav bar**: `.glassNavBar()` modifier. Large title on Cameras, inline on sub-screens.

## Engineering Standards

### SwiftUI
- `@StateObject` for models owned by a view, `@ObservedObject` for passed-in models
- `@EnvironmentObject` for AppState — never drill props through 4 layers
- `.task {}` for async work tied to a view's lifetime — always cancellable
- Never use `DispatchWorkItem` — use `Task` with `Task.isCancelled` checks
- Never use `Timer.publish().autoconnect()` without `.onDisappear { cancel }` — use Task loops instead
- Animations: always check `@Environment(\.accessibilityReduceMotion)` before animating

### AVFoundation
- Always remove time observers BEFORE nilling the player (capture player ref first)
- `AVAudioSession` category: `.playback` for video with audio, `.ambient` for muted background
- PiP: use `AVPictureInPictureController` — already wired in `LivePiPController`
- Stop players on `.onDisappear` unless `persistent: true` is explicitly set

### Networking (added after the app took the NVR down — see HANDOFF §10)
- **Never `URLSession.shared` for Frigate.** Its `timeoutIntervalForResource` is 7 days. Use
  `FrigateClient.apiSession`, `FrigateClient.downloadSession`, or `BoundedSession`.
- **`request.timeoutInterval` is an IDLE timeout and does not bound a request.** Frigate streams
  previews/snapshots/exports out of an ffmpeg pipe; a trickling pipe resets that timer forever. The
  session's `timeoutIntervalForResource` is the only real cap.
- **Abandoning a request costs the SERVER, not just the client.** An unread ffmpeg pipe blocks
  forever and holds a Frigate API worker. 40 of those killed the whole API for 7 hours.
- Cap `httpMaximumConnectionsPerHost`; never let a nine-camera view fan out as nine requests.
- Any repeating fetch needs a failure path: back off, and slow down when the server is slow. A
  fixed tick with no error handling is how the wall added load to a server already failing.

### Memory
- All closures that reference `self` in async contexts use `[weak self]`
- `NotificationCenter` observers stored and removed on deinit/disappear
- `Timer`-based or `Task`-based loops always cancelled on view disappear

### Build
- Zero warnings target — treat every warning as an error
- No force unwraps (`!`) except in `layerClass` overrides where `fatalError` is appropriate
- No `TODO:` or `FIXME:` comments in production code

## How to Build

```bash
# 1. Regenerate Xcode project (run after any project.yml change)
cd ~/apexsight/native-ios && xcodegen generate

# 2. Build for simulator (check for errors)
xcodebuild \
  -project ApexSightNative.xcodeproj \
  -scheme ApexSightNative \
  -destination "platform=iOS Simulator,name=iPhone 16 Pro" \
  -configuration Debug \
  build 2>&1 | grep -E "error:|warning:|Build succeeded|Build FAILED"

# 3. Clean build (when you need a fresh slate)
xcodebuild \
  -project ApexSightNative.xcodeproj \
  -scheme ApexSightNative \
  -destination "platform=iOS Simulator,name=iPhone 16 Pro" \
  clean build 2>&1 | grep -E "error:|warning:|Build succeeded|Build FAILED"

# 4. Install and launch on booted simulator
APP=$(find ~/Library/Developer/Xcode/DerivedData -name "ApexSightNative.app" \
  -path "*/Debug-iphonesimulator/*" | head -1)
xcrun simctl install booted "$APP"
xcrun simctl launch booted com.brandontoth.apexsight.native

# 5. Get console logs
xcrun simctl spawn booted log stream --predicate 'subsystem == "com.brandontoth.apexsight.native"'
```

## Testing on the simulator

The `mcp/ios-tester` MCP (screenshot/tap/swipe/type/console) was **fixed** — its old tap/swipe
called a non-existent `simctl io tap`. It now maps device logical points → macOS desktop points
from the live Simulator window frame and drives `cliclick`, activating the Simulator first (a
click on a background window only focuses it). **Restart Claude Code to load the rebuilt MCP**
(`cd mcp/ios-tester && npm run build`). It auto-detects device size (iPhone 17 Pro = 402×874).

Coordinate notes (402×874): tab bar Y ≈ 830; tabs x ≈ Cameras 70, Review 134, Activity 201,
Explore 273, Settings 343. Run taps so the Simulator is frontmost first.

**Limits:** synthetic clicks don't reliably trigger SwiftUI **Menus**, the **zoom-scrollview tap**
(full-screen chrome toggle), or custom **drag** gestures. For those, verify via build + code review
and confirm on a real device. To reach a screen behind such a gesture, inject a deep link:
`apex://review?id=…` / `apex://event?id=…` / `apex://camera?name=…` written to the app-group plist
`apex.pendingIntentLink`, then cold-launch (consumed on launch). `simctl spawn defaults` writes the
WRONG container — write the real one at `…/Shared/AppGroup/<uuid>/Library/Preferences/group.com.brandontoth.apexsight.plist`
and reboot the sim so cfprefsd reloads. A standalone `scratchpad/simtap.py` does the same mapping if the MCP isn't reloaded yet.

Real Frigate is connected in the sim (`frigate.plexserver525.com`, 8 cameras). Always test new
work against it, then **ship to TestFlight** per the workflow at the top.

## Known Issues to Fix (Start Here)

This app is well past its initial bring-up (build 158+, user-verified working). The original
start-here list is done: camera black-flash (fixed build 151 via `isReadyForDisplay`), empty
states, badge counts, etc. **The `stasel/WebRTC` package is NOT dead — do NOT remove it**; it
powers both two-way talk (`TwoWayTalkController`) and the sub-second live overlay
(`RealtimeVideoController`). Any earlier note to strip it is stale.

Current watch-items (from the build-158 streaming work):
- **Doorbell first-open cold-start (~8s)** — its go2rtc stream is an ON-DEMAND NVENC re-encode,
  so the very first watch per session spins up ffmpeg before it paints (the 10s fallback timer
  covers it). Could be smoothed by pre-warming the stream when the wall loads.
- **MJPEG fallback keys off `.playing`, not real frames** — a stream that reports `.playing` but
  never renders (the pre-fix doorbell failure mode) would sit on a frozen snapshot with a long
  timer. The server-side ffmpeg fix removed the trigger, but keying the fallback off `videoReady`
  would harden it against any future recurrence.
- **Wall uses full `main` for sub-less cameras** (doorbell/movie_room have no `_sub`) — heavier
  than needed; real `_sub` streams would lighten the grid.
